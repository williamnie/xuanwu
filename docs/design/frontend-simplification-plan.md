# 玄武前端精简方案

> 状态：草案 v3（2026-10-13）。经 Codex 会话对照代码两轮只读评审（基线 `9acf05d6`）后修订，评审结论见第 11 节。
> 范围：`frontend/` 的信息架构、导航、页面结构、交互和文案；**不改变视觉语言**。
> 视觉仍以 `docs/design-system/spec.md` 为准；本方案如需新增组件，先回写 `docs/design-system/components.css` 和 spec，再在页面中使用。
> 本文的“删除”一律指**从 Web UI 中移除入口**；后端 API、CLI 和数据都不受影响。需要新增后端合同的改动单独列在第 8.2 节，不混入纯前端阶段。

## 1. 背景：玄武是做什么的

玄武是一个让编程 Agent 持续工作的控制平面。用户把要做的事写成任务（Issue），玄武把任务派给 Codex / Claude Code / Pi / Qoder 执行，中断时自动恢复，结束后检查实际结果（测试、Git 变更、验证命令），只在需要人判断时回来找用户。

README 给出的核心用法只有一句话：**列好 Issue，告诉玄武开始，卡住了它会问你。** 用户真正关心的只有四步：

```
写任务 → 玄武去做 → 需要我时处理 → 看结果
```

前端的一切设计都应该服务这四步；除此之外的内容默认收起或移到“高级”。

## 2. 现状问题

用户反馈的“繁琐、上手难”，根因是**前端把后端的内部模型原样暴露给了用户**。

| # | 问题 | 例证 |
|---|---|---|
| P1 | 概念太多，中英混杂 | 用户同时面对 Work、Issue、Run、Attempt、Session、Evidence、Handoff、Supervisor、Code Agent、Provider、Agent Profile；任务详情有 `Execution routing / Effective provider / Selection source`（`pages/WorkDetail.jsx:318`） |
| P2 | “让玄武干活”有 4 个入口，行为各不相同 | 工作台“交给玄武”、问玄武对话、全局 Ask 输入框（`components/GlobalAskComposer.jsx`）、看板“新建工作” |
| P3 | 一级导航有 7 项 | 工作台、问玄武、工作项、运行记录、自动化、统计分析、设置（`pages/assistantModules.js`） |
| P4 | 默认视图是 7 列看板 | triage/todo/in_progress/needs_user/failed/done/cancelled（`pages/workBoardModel.js:1`）；多数用户只想知道“哪些要我管” |
| P5 | 看一次结果要跳三层 | 工作项 → 运行记录 → 会话记录；验证结果和交付结果在另外的 Tab |
| P6 | 工作台堆了 7 块 | 健康条、告警横幅、4 个数字、需关注、进行中、最近交付、4 个跳转链接（`pages/Dashboard.jsx`） |
| P7 | 新建任务暴露内部状态 | 要在 triage/todo 之间选初始状态，并显示 `Effective: … （Work 显式）`（`pages/work/WorkEditorDialog.jsx`） |
| P8 | 首次引导 6 步，错误文案是后端术语 | 提示里出现 `xuanwu doctor`、“Issue-backed Work authority”、“passed Evidence”（`pages/command-center/firstDeliveryGuideModel.js`） |
| P9 | **设置页过载** | 11 个 Tab + 4 个连接子 Tab + 20 多个面板；同一配置出现在两处；只读开发者信息放在“常用”位置。详见第 6 节 |

## 3. 设计原则

1. **先“我需要做什么”，后“系统在做什么”。** 首屏只放需要用户决定的事。
2. **一套共用流程，多个就近入口。** 同一件事（如创建任务）只有一套表单和逻辑，可以从侧栏、空状态、项目上下文打开，并带上当时的上下文。
3. **默认值可用，就不让用户选。** 能自动检测、能继承、能推断的字段收到“更多选项”。
4. **用户的词，不是后端的词。** 界面用中文业务词；英文只留在 ID、日志和 spec 规定的 mono 微标签里。
5. **默认收起，能力保留。** 低频功能先收起而不是删除；只有确认无用（无操作、无数据依赖）的展示才删除。
6. **动作语义来自后端。** 待处理卡片、按钮文案、提交参数都以后端返回的请求类型和版本为准，前端不把它们简化成通用的状态更新。
7. **旧值无损。** 移动或隐藏字段后，编辑其他字段时必须原样保留旧值，不得清空或隐式改写。
8. **视觉不动。** 只改结构、交互和文案，遵守 `docs/design-system/spec.md` 的全部禁忌。

## 5. 信息架构

### 5.1 一级导航：7 项 → 3 项 + 设置

| 新导航 | 内容 | 合并了原来的 |
|---|---|---|
| **待我处理**（首页） | 只放需要用户决定的事 | 工作台 |
| **任务** | 任务列表、自动化 | 工作项、自动化、运行记录 |
| **对话** | 与玄武助手对话 | 问玄武 |
| 设置（底部） | 见第 6 节 | 设置 |
| 统计（底部“更多”菜单） | 不变 | 统计分析 |

**路由 ID 分两步改：**

- **第一批（B0）只改导航显示名和顺序**，保留现有 canonical route ID（`command-center`、`work`、`runs`、`automations`、`settings` 等），地址不变，所有深链自然兼容。“运行记录”“自动化”要等 C1 在任务详情和任务页里提供了替代入口后，才从一级导航移除（见 8.1）。
- **路由改名（如 `inbox`、`tasks`）放到后面单独一批**，前提是先写好路由状态合同的覆盖测试。迁移必须覆盖以下 5 类情况，不能只改 `PRODUCT_COMPAT_ROUTE_REDIRECTS`：
  1. `#/work/<id>`、`?workId=`、旧 `issueId` 到 Work ID 的转换、Handoff 专用深链（`appRouteModel.js:32–85`、`handoffPageModel.js`）。
  2. `runId` 优先于 `sessionId`；解析失败、找不到所属任务、或执行记录不属于任何任务时，**保留只读查看页**作为退路，而不是静默跳到列表。
  3. `conversationId`、项目和筛选上下文、`workBoard` feature flag 的兼容。
  4. 设置的 `section` 参数同时接受裸值（`diagnostics`）和 `advanced:diagnostics`（`settingsNavigation.js:61–68`），打开后自动展开对应折叠区并滚动定位。
  5. 后退/前进、复制链接、刷新后仍定位到同一对象。

### 5.2 共用的任务创建流程

- 侧栏顶部放“新建任务”按钮（spec 5.4 规定的唯一品牌渐变按钮），支持快捷键 `Ctrl/Cmd+K`。任务列表空状态、项目上下文中也可以打开**同一个**创建流程，并带上当前项目。
- 工作台的“交给玄武”按钮删除（它实际跳到对话，容易和创建任务混淆）。全局 Ask 输入框保留为“问玄武”的快捷入口，文案明确是“提问”，不是“创建任务”。
- 表单字段：
  - **项目**：默认取打开时的上下文项目，否则取上次使用的项目；只有一个项目时不显示选择器。
  - **描述**：必填。标题字段默认收起，留空时从首行自动生成（现有逻辑已支持）。
  - **加入执行队列**：**默认不勾选**，即保持现有默认值“待确认”（`triage`，`work/workProfileRouting.js:6`；已由产品决定，Q8）。用户勾选后为 `todo`。文案**不承诺“立即开始”**：只有项目开启自动执行（`project.auto_run=1`，`backend-ts/src/http/workApi.ts:477`）且没有暂停、依赖已就绪、编程工具可用时，才会被调度（`projectLoop.ts:79–105`）。不满足时，提交后直接提示原因，例如“项目已暂停，恢复后开始”。
  - **执行预设**：收在“更多选项”，默认“跟随项目设置”（即回到项目的执行默认值，不是“不用编程工具”）。只映射到现有的 `agent_profile_id`（`workApi.ts` 白名单不接受任务级 provider/model），**不新增任务级模型覆盖**，也不通过修改项目默认值来实现单个任务的覆盖。
  - 编辑已有任务时，如果原来选中的预设现在不可用，下拉中显示为“当前选择（不可用）”的禁用项，保留原值，不隐式切换。
  - 删除 `Effective: … （Work 显式）` 预览串，改为一句中文说明“将使用：Codex · gpt-x（来自项目设置）”。
- **批量创建：Web UI 不做**（产品决定 Q12，2026-10-15）。人工在界面里一次建一个任务；多任务拆分由 Agent 通过 `skills/xuanwu` 的 “Batch Creation and Dependencies” 合同完成（先全部以 `triage` 逐条创建、补依赖、读回校验，只入队夜间可执行项）。逐条创建各自带 `audit.event_id`，部分失败可只重试未创建的条目；不新增批量 HTTP 接口。

### 5.3 首页“待我处理”

替换现在的工作台（`pages/Dashboard.jsx`）。从上到下：

1. **待你处理**（主体）：卡片列表。**卡片的类型、文案和按钮由后端的请求类型决定**，不按任务状态推导：

   三类来源的读取、提交和冲突规则各不相同，前端为每类写**独立的处理逻辑**，不写一个“通用批准”函数：

   | 来源 | 请求类型（机器值） | 读取 | 提交 | 可选动作 | 冲突与校验 |
   |---|---|---|---|---|---|
   | 任务人工审核（HumanReview） | `decision`、`acceptance`、`risk_acceptance`（`domain/review/humanReview.ts:37–51`） | `GET /api/works/:id` 的 `decision.request` | `POST /api/issues/:id/human-review-response` | 只有 `accept` / `reject` / `request_changes` 三种（`humanReview.ts:670–673`）；`reject` 和 `request_changes` 必须填意见 | 携带 `review_request_id` + `review_revision` |
   | 待处理事项（Attention）中的决策：执行工具审批、操作提案、助手动作 | `decisions[].kind`：provider approval / proposal / pi_action | `GET /api/command-center/attention/:id` 的 `decisions[]`（含 `kind` / `ref` / `gate` / `status`） | `POST /api/command-center/attention/:id/actions/:action`（`commandCenterApi.ts:642–759`） | 按 `gate.can_approve` 和状态决定是否可操作 | 指定关联的 `decision_ref`，带该对象接受的 actor / reason / comment / scope；执行工具审批默认 turn 级范围 |
   | 失败的任务 | — | 任务列表与 `availableActions` | 现有任务动作（retry 等） | 按 `availableActions` | `expected_revision` + audit |

   卡片文案：
   - `decision`：问题、建议、影响（`question` / `recommendation` / `consequences`）；按钮“确认决定”“要求修改”“拒绝”，后两者附意见框。**现有合同没有结构化选项**，前端不得从自然语言里解析出多个选项；要做选择题，需另立请求/响应合同。
   - `acceptance`：结论、验收要点、验证状态；按钮“验收交付”“要求修改”。
   - `risk_acceptance`：风险、影响范围、排除范围；按钮“授权并继续”“拒绝”。
   - Attention 决策：要执行的操作、来源、风险；按钮按 `gate` 显示“批准”“拒绝”。
   - 失败任务：失败原因一句话；按钮“重试”“查看详情”。

   - 卡片的 key 用“来源类型 + 原始请求 ref”，`work_id` / `attention_id` 只作为关联字段。不按 `work_id` 合并（会吞掉同一任务的多个请求），也要去掉同一提案通过多个 Attention 来源重复出现的情况。
   - 只有 Attention 的 acknowledge / snooze 使用 `expected_revision` + audit（`commandCenterApi.ts:767–785`）；不要给所有决策都加 `expected_revision`，也不要宣称后端有统一的版本校验。
   - 收到 409 或“已失效”时，按来源分别处理：刷新该卡片，并说明是内容已更新、已在别处处理，还是请求已过期，不一律提示“请重新确认”。
   - **审批可能没有关联任务**，首页的数据来源是待处理请求的聚合，不是任务列表。现有 Attention 汇总接口（`/api/command-center/summary?sections=attention`）默认 10 条、最多 25 条，助手动作只读 7 天窗口，且不聚合任务的人工审核请求，**不能当作完整收件箱**；完整首页依赖第 8.2 节的聚合方案。读取失败或结果被截断时，不得显示“没有需要你处理的事”。
   - 任务状态是 `needs_user` 但还没有人工请求（仍由玄武助手持有）时，显示为“玄武正在整理问题”，不显示可操作按钮。
   - 提交成功后的提示按实际返回写，例如“已提交，玄武会在新的一轮执行中处理”；**不无条件承诺“任务已继续”**。“要求修改”会在同一会话里开新的一轮执行，如果恢复失败，请求会重新打开。
   - 列表为空时显示空状态：“没有需要你处理的事”，附“新建任务”按钮。
2. **执行中**：紧凑列表，最多 5 行，“查看全部”跳到任务页；被阻塞的任务显示阻塞原因（等待依赖 / 项目已暂停 / 编程工具未就绪）。
3. **今天完成**：紧凑列表，最多 5 行。

**删除**：顶部 4 个统计数字、底部 4 个跳转链接。
**修改**：`RuntimeHealthStrip` 和 `GuardianAlertBanner` 只在**异常时**显示，作为页面顶部一条告警。

### 5.4 任务页

- **默认列表视图**。顶部只有 4 个筛选：**进行中**（排队中 + 执行中）、**待你处理**（待确认 + 待你处理 + 失败）、**已完成**、**全部**（含已取消）；另有项目、来源（全部 / GitHub / 手动）筛选和搜索。
- 列表行：状态点 + 标题 + 项目 + 最近一句进展或阻塞原因 + 更新时间。
- **看板保留为可切换的视图**。拖拽保留现有受门禁保护的语义：拖拽映射为 enqueue / retry / cancel / update，且禁止直接拖到 done / failed / needs_user（`workBoardModel.js:78–93`）。在列表视图里，同样的操作以明确的按钮提供。
- 顶部子视图：**任务** | **自动化**。自动化即原 `pages/Automations.jsx`：
  - 搜索和项目筛选默认可见；状态和触发方式筛选收进“筛选”菜单，但必须能找到已暂停、异常的自动化，以及每种触发方式（cron / continuous / manual / webhook）。
  - 列表行直接显示触发方式和状态。
- 删除表头的“共 N 条 / 已加载 N 条”计数文案。“刷新”按钮改为图标按钮，留在原位。

### 5.5 任务详情：常驻状态 + Tab（Q11）

取代 `pages/WorkDetail.jsx` 的“概览 / 交付 / 活动”三个 Tab，也取代后来的单页三段式（长描述会把结果和执行挤到看不见）。

1. **常驻区（不在 Tab 里）**
   - 页头：标题、状态、项目、更新时间；唯一主操作按钮随状态变化（开始 / 重试），次要操作（编辑、取消、复制任务 ID）在旁边。
   - **现在怎样**：一句话说明当前状态；被阻塞时写明原因；**所有未处理的请求（问题、审批、验收）都在这里**，切换 Tab 不会藏起来。按钮规则同 5.3。
2. **Tab**（`结果 / 任务描述 / 执行 / 活动`，标签带数量）
   - **结果**：合并展示原“交付结果”（Handoff）和“验证结果”（Evidence），但**保留以下区别，不合成一个“完成”绿勾**：每条验证结果属于哪一次执行、来源、时间、是否过期；交付各阶段分开显示（执行成功、验证通过、PR 已创建、已合并、已部署）；改动的文件、PR 链接、玄武的总结。没有结果时显示一句空状态。
   - **任务描述**：任务目标全文和自定义验收标准。
   - **执行**：执行列表（Q10），每行跳到执行记录页并定位；底部折叠“执行配置”（使用的编程工具、模型、来源、实际执行时使用的工具）。
   - **活动**：活动时间线，首次打开该 Tab 才请求。
3. **默认 Tab**（`workDetailModel.js` 的 `defaultWorkDetailTab`）：深链带交付 ID → 结果；带 `runId` → 执行；待确认 / 排队中 → 任务描述；执行中 → 执行；其余（完成、失败、待你处理、已取消）→ 结果。只在首次打开任务时选择，状态刷新不抢走用户手动选的 Tab；从执行记录页“所属任务”回来时切到执行并高亮那一次。

**删除**：页头的 `WORK ID` 标识块（移到“…”菜单）。

### 5.6 执行记录页

**保留在一级导航**（改名“执行记录”，见 Q9）。它是查看单次执行完整过程的唯一入口（Q10）。执行详情顶部提供“所属任务”链接（`#/work?workId=…&runId=…`，打开任务并选中这次执行），**不自动跳转**。不属于任何任务的执行记录、独立 provider session 也在这里查看。

### 5.7 首次引导：6 步 → 3 步

现在的 6 步（`firstDeliveryGuideModel.js`）：玄武可以运行 → 选择谁来做 → 配置玄武 → 告诉玄武项目在哪 → 启动第一个 Issue → 看到执行结果。

新的 3 步：

1. **准备 AI**：把“选编程工具”和“连接玄武助手”合成一步。
   - 自动检测本机已就绪的编程工具并预选。

### 6.2 主要问题

1. **同一配置出现在两处**
   - Codex 运行方式（CLI / App）：编程工具页的“Codex 运行方式”和运行维护页的“Codex server 接入方式”，改的是同一个设置。
   - 编程工具状态：编程工具页的检测卡片和运行维护页的 `Provider Settings` 卡片，展示的是同一类信息。
   - 首次使用：运行维护页的“首次使用启动器”安装教程与首次引导、README 重复。
2. **只读信息占据常用位置**：“执行权限”是常用组第 3 项，但整页只读，还会看到 `capabilityID` 这类代码。
3. **一个页面里标题重复三层**：设置页头 → 分区标题与说明（`SettingsSectionIntro`）→ 面板自带的 h2 与说明（如“项目与偏好”下又有“项目管理”，“编程工具”下又有“编程工具”）。
4. **字段过多且是原始格式**：飞书要填 5 个 `oc_xxx/ou_xxx` 原始 ID 和映射字符串；Telegram 的项目映射也是原始字符串。
5. **开发者诊断信息混在一起**：运行状态里有进程组内存、RSS P95、PID 列表；活动记录要求填 raw event / proposal ID。
6. **低频配置平铺**：API 协议、表达风格、Prompt 摘要等都平铺在同一页。

### 6.3 新结构：4 个常用分区 + 1 个高级

```
设置
├─ 项目
├─ AI 连接          （编程工具 + 玄武助手）
├─ 通知与外部连接    （通知 + GitHub / 飞书 / Telegram）
├─ 通用            （语言、表达风格、版本与更新）
└─ 高级            （单页，分节折叠）
   ├─ 运行维护
   ├─ 安全与权限
   ├─ 技能与工具
   ├─ 记忆
   ├─ 执行预设
   └─ 处理记录
```

导航从 11 项变为 5 项。“高级”是一个页面，内部用 `<details>` 分节（复用现有 `settings-disclosure` 组件），默认全部折叠；通过深链进入时自动展开目标节并滚动定位。

**通用规则**（适用于所有分区）：
- **删除**面板内部重复的 h2 和说明段，只保留 `SettingsSectionIntro` 一层标题。
- **删除**设置页头的说明句，只保留标题。
- 低频字段统一收进“更多选项”折叠区，不再出现“高级运行配置（可选）”“Profile 覆盖项（高级）”“安全与高级设置”等多种叫法。
- 移动或收起的字段在保存时**原样保留旧值**（原则 7）；revision / 草稿冲突保护保持不变。
- **折叠区和抽屉首次展开才挂载面板**（延续现有 `AssistantSettingsSections.jsx` 按 Tab 挂载、MCP 按 `toolsVisited` 挂载的做法）。很多面板挂载即发请求（如 `PiMemoryPanel.jsx:55`、`SkillsRuntimePanel.jsx`），如果把所有面板放进关闭的 `<details>`，进入“高级”就会同时请求技能、MCP、记忆、活动和日志。展开过的面板在收起时保留状态，不丢未保存的草稿；通过深链进入时只初始化目标面板。
- **每个设置域只有一个表单状态的所有者**。跨分区移动字段（如表达风格）或改成抽屉（如 GitHub）时，不能出现两份表单同时编辑同一份配置、互相覆盖。

## 7. 设计系统约束

- 不新增颜色、圆角、字号、阴影、图标和动效；所有新页面复用 `docs/design-system/tokens.css` 的令牌。
- 需要新增的组件（先写入 `components.css` 和 `spec.md`，再使用）：
  - **待处理卡片**（首页“待你处理”）：`--surface-raised` 底、1px 边、`--radius-md`，左侧 status-dot，右侧操作按钮组；不得做成大面积彩色卡片。
  - **任务列表行**：沿用侧边栏列表项的 hover / active 规则（spec 5.4）。
  - **设置抽屉**：右侧浮层，`--surface-overlay` 底，宽度 480px，760px 以下全屏；不用毛玻璃（spec 4.1 只允许三处）。
- “新建任务”按钮使用 spec 5.4 规定的唯一品牌渐变；首页其他按钮遵守“单点强调”，每屏只有一个主按钮。
- 微标签仍用 mono 大写英文（spec 8），但正文、标题、按钮文案全部改用第 4 节的中文术语。
- 每批完成后检查浅色、深色主题和 980 / 760 / 680px 三个断点，并运行前端样式测试。

| Q4 | 低频、只读的功能是否保留？ | 不需要给用户看的可以删除。判断标准：没有可操作按钮、不影响执行行为、且信息在别处可得或对用户无意义。按此删除：Plugin 意图、助手生效配置摘要、通知历史规则列表、IM channel 注册表、运行状态明细卡（数据在诊断包中）、能力标识代码列。保留：Skill 意图（影响预设匹配）、当前通知规则的停用操作、技能运行记录（排查自定义技能）、处理记录、来源策略与审批规则（安全透明） |
| Q8 | 新建任务默认值 | 保持“待确认”（`triage`），不自动加入执行队列 |
| Q9 | 执行过程的可见性 | 第一版精简实现把执行过程折叠成只读记录、并把运行记录页自动跳回任务，用户反馈“看不到任务的执行情况”。决定：任务详情“过程”默认展开并复用完整执行视图；“执行记录”保留在一级导航，不自动跳转 |
| Q10 | 任务详情与执行记录的分工 | Q9 的方案让任务详情和执行记录页显示同一份完整执行视图，用户反馈两处重复。决定：任务详情只保留与任务相关的信息（现状、交付总结、执行列表），完整过程只在执行记录页看；任务详情每次执行一行，可跳转并定位到该执行。执行记录页的“所属任务”链接保持不变 |
| Q11 | 任务详情的版式 | 单页三段式下任务描述很长时，结果和执行被挤到下面看不到。决定：页头和“现在怎样”（含待处理请求）常驻，其余放进“结果 / 任务描述 / 执行 / 活动”四个 Tab；默认 Tab 按深链和状态选，没开始看描述、执行中看执行、结束后看结果 |
| Q12 | 批量创建是否进 Web UI | 不进。人工在界面里通常一次建一个任务；批量拆分是 Agent 的场景，已由 `skills/xuanwu` 的批量创建与依赖合同覆盖（逐条创建、逐条幂等），不新增批量接口 |

## 10. 效果衡量

先测量当前基线，再设目标；在基线出来前，不把任何百分比当作承诺。

| 指标 | 说明 |
|---|---|
| 首个任务完成率 | 新用户完成首次引导并看到交付结果的比例 |
| 首个任务耗时 | 从打开页面到第一个任务开始执行 |
| 响应待处理请求的耗时 | 请求出现到用户提交的时间；点击数作为辅助指标 |
| 找到配置的成功率 | 可用任务式可用性测试（“去把 GitHub 的自动修复打开”）测量 |
| 失败恢复成功率 | 失败任务经用户重试或处理后最终完成的比例 |
| 完成交付时间 | 任务创建到交付结果产生 |

“设置页访问减少”不单独作为成功指标：访问减少也可能是因为入口找不到了。
